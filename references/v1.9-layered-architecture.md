# Juanjuan Team v1.9 分层调度架构

**核心设计**：按任务复杂度分层调度——Lite/Medium 用 Agent Teams teammate，Complex 用 `claude -p` 真独立进程。7 主角色都是项目组，可 spawn 自己的 sub-agent team。

---

## 一、任务分级

| 级别 | 判定标准 | spawn 方式 | 隔离性 |
|------|---------|----------|--------|
| **Lite** | 单文件 / 不跨模块 / 无架构影响 / 无新功能 | Agent Teams teammate | 同进程独立 context（已验证 0 泄漏） |
| **Medium** | 2-5 文件 / 跨 1-2 模块 / 新功能但不跨模块 | Agent Teams teammate | 同进程独立 context |
| **Complex** | >5 文件 / 跨 ≥3 模块 / 安全关键 / 大型系统设计 | **`claude -p` 真进程** | 完全独立 OS 进程（进程级隔离） |

### 1.1 判定脚本

`scripts/task-classify.sh` 接收任务描述 + 文件清单，输出 `Lite | Medium | Complex`。

判定逻辑：
- 涉及文件数 ≤1 + 不跨模块 → Lite
- 涉及文件 2-5 / 跨 1-2 模块 → Medium
- >5 文件 / 跨 ≥3 模块 / 安全关键（auth/payment/PII）/ 大型架构设计 → Complex

卷卷可显式覆盖（说"用 Lite" / "用 Complex"）。

## 二、Lite/Medium 路径（Agent Teams teammate）

### 2.1 spawn 方式

用 Claude Code 的 `Agent` 工具，带 `name` 参数让 teammate 持续运行：

```
Agent({
  subagent_type: "juanjuan-architect",
  name: "architect",
  prompt: "...",
  run_in_background: true
})
```

### 2.2 通信

- convener 用 `SendMessage({to: "architect", message: "..."})` 跨 teammate 通信
- teammate 完成后发回结果（通过 teammate-message 事件）

### 2.3 适用场景

- TODO list 数据结构设计（v1.8 已验证）
- 单文件 bug 修复
- 小工具脚本
- 简单 API 端点

### 2.4 隔离性保证

- teammate 独立 context，看不到主会话历史
- convener 不把 architect 的 reasoning.md 塞进 reviewer 的 prompt（盲审硬约束）
- spawn 前 grep 检测策略性语言（"考虑过""担心"等），阻断 + 打回 architect 重写

## 三、Complex 路径（`claude -p` 真进程）

### 3.1 spawn 方式

`scripts/global-spawn.sh` 启动完全独立的 Claude 进程：

```bash
claude -p \
  --output-format stream-json \
  --append-system-prompt "$(cat ~/.claude/agents/juanjuan-architect.md)" \
  "<prompt>" > "$team_dir/outputs/architect.jsonl" 2>&1 &
```

每个主角色是一个独立 OS 进程，PID 记到 `<team_dir>/<role>.pid`。

### 3.2 通信

进程间不能直接 SendMessage（不同进程），用**文件消息协议**：

```
~/.juanjuan/teams/<team-name>/mailbox/
  ├── convener_to_architect_001.json
  ├── architect_to_convener_001.json
  ├── architect_to_reviewer_001.json (盲审请求 + design.md 路径)
  └── reviewer_to_convener_001.json (review.json 路径)
```

每个 agent 轮询自己的收件箱（`*_to_<role>_*.json`）。

### 3.3 专属 Mailbox（独立消息队列）

每组 Complex team 一个独立目录，互不干扰：

```
~/.juanjuan/teams/<team-name>-<timestamp>/
├── mailbox/                     # 专属消息队列
│   ├── convener_architect_001.json
│   ├── architect_convener_001.json
│   ├── architect_reviewer_001.json
│   └── reviewer_convener_001.json
├── outputs/                     # 每个 agent 的 stream-json 输出
│   ├── architect.jsonl
│   ├── reviewer.jsonl
│   └── convener.jsonl
├── audit/                       # 独立审计日志
│   └── events.jsonl
├── architect.pid                # 进程 ID
├── reviewer.pid
└── convener.pid
```

### 3.4 适用场景

- 大型系统设计（百万用户登录系统、支付系统）
- 跨模块重构
- 安全关键任务（auth/payment/PII）
- 多 Agent 多轮辩论需要持续运行的场景

### 3.5 隔离性保证

- 真独立 OS 进程（Activity Monitor 能看到独立 `claude` 进程）
- 进程间无共享内存，无共享 context
- 完全平等的独立 Claude 实例
- mailbox 是文件消息，agent 主动读，不被动接收

## 四、7 主角色 = 7 项目组

### 4.1 项目组结构

每个主角色下面可以有自己的 sub-agent team：

```
reviewer (主角色，项目组负责人)
├── typescript-reviewer (sub, 帮审 TS 类型)
├── security-reviewer (sub, 帮审 OWASP)
├── silent-failure-hunter (sub, 帮审静默失败)
└── type-design-analyzer (sub, 帮审类型设计)

architect (主角色)
└── code-architect (sub, 帮分析现有架构)
└── code-explorer (sub, 帮探索代码库)

coder (主角色)
├── tdd-guide (sub, 帮 TDD)
├── build-error-resolver (sub, 帮修 build)
└── language-specific-reviewer (按语言)
```

### 4.2 关键约束（卷卷强调）

- ❌ **Sub agent 不能是独立主角色**——sub 不能顶替 reviewer 做 verdict
- ✅ **Sub agent 帮主角色做细分任务**——主角色汇总 sub 的 finding 后做 verdict
- ✅ **7 主角色都是项目组**——每个主角色都可以 spawn 自己的 sub team
- ✅ **sub 是辅助**，不是决策者

### 4.3 sub 调用方式

主角色在 prompt 里写："调 Agent 工具 spawn 一个 typescript-reviewer sub 帮审 TS 类型"，Claude 读到后自己调 Agent 工具。

```
Agent({
  subagent_type: "typescript-reviewer",  // 用 ECC 内置的 sub
  description: "审 src/auth/login.ts 类型安全",
  prompt: "...",
  run_in_background: true
})
```

### 4.4 sub 数量

| 主角色 | sub 数量（Safe 模式） | sub 数量（YOLO 模式） |

| convener | 3 | 1 |

## 五、冗余恢复机制（v1.9 新增）

### 5.1 phase-state.json

每个项目目录加 `.convener/phase-state.json`：

```json
{
  "task_id": "<项目目录名>",
  "current_phase": "Phase 3",
  "current_phase_status": "in_progress",
  "in_progress_agent": "reviewer",
  "in_progress_started_at": "<ISO 8601>",
  "completed_phases": ["Phase 0", "Phase 1", "Phase 2"],
  "last_updated": "<ISO 8601>"
}
```

### 5.2 恢复流程

Claude 重开后，convener 读 phase-state.json：

```
读 .convener/phase-state.json
  ↓
发现 current_phase_status = "in_progress"
  ↓
检查对应 agent 的产出文件是否完整
  ↓
完整 → 标记完成，继续下一 Phase
不完整 → 清理脏数据 + 重新 spawn
```

### 5.3 脏数据清理

`scripts/cleanup-stale.sh` 检查 in_progress agent 的产出：
- 检查 architect 的 design.md 是否写完（有"# Design"开头 + "## 9. 风险点"结尾）
- 检查 reviewer 的 review.json 是否合法 JSON
- 不完整 → 备份到 `.audit/stale-<timestamp>/` + 删原文件

## 六、project-id 聚合 + registry.json

### 6.1 目录命名升级

```
~/项目/<project-id>-<timestamp>-<rand4>/
例：
~/项目/todo-list-2026-08-05-0052-5bf9/
~/项目/todo-list-2026-08-06-1430-a3f2/  ← 同 project-id 不同时间
```

卷卷第一次说"这个项目叫 todo-list"，后续都在这个 project-id 下加时间戳。

### 6.2 registry.json

`~/.juanjuan/registry.json`：

```json
{
  "todo-list": {
    "first_created": "2026-08-05T00:52:00Z",
    "project_dirs": [
      "~/项目/todo-list-2026-08-05-0052-5bf9/",
      "~/项目/todo-list-2026-08-06-1430-a3f2/"
    ],
    "latest_dir": "~/项目/todo-list-2026-08-06-1430-a3f2/",
    "status": "active | completed | paused"
  }
}
```

卷卷说"接着跑 todo-list" → convener 查 registry → 找 latest_dir → 读 phase-state.json 接着跑。
